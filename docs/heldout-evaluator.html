The complete guide

The held-out evaluator

An AI agent skill for GitHub Copilot or Claude Code that takes one Jira story, writes independent acceptance tests from the requirement alone, runs them against the live application, and hands a person an evidence-backed recommendation: does the app do what the story asked for?

What it is

In plain English

Imagine an exam written by someone who has read the syllabus but has never seen the student's homework. That is a held-out test. The term comes from machine learning, where you keep some data aside so a model can't simply memorise the answers.

Here, the "syllabus" is a Jira story and the "student" is your application. The evaluator reads only the story: its title, description and acceptance criteria, the screenshots they show and the Confluence pages they link. It never looks at the application's code or the developers' own tests. So when a test fails, it's a sign that the application drifted from what was asked for, not that the test copied a mistake.

It never files bugs by itself. It writes a verdict with evidence and reproduction steps, and a person confirms or rejects each finding.

Independent

Tests come from the requirement only. The expected values are sealed before the tests ever touch the application.

Evidence first

Every requirement is quoted from cited lines. Every failure is reproduced live and shipped with curl commands, screenshots and traces.

A person decides

The verdict is a recommendation with a confirm, reject or clarify box per finding. It creates no Jira issues.

Who does what
  • You ask Opus, in GitHub Copilot's agent mode or in Claude Code: "Run a held-out evaluation of ABC-123." You answer questions only you can answer, such as what a vague criterion means.
  • Opus follows the skill: it reads the story, writes the tests, hardens them against the app, triages failures and writes the verdict.
  • Five subagents do the phases that need a model, each in a fresh context: the contract extractor and its independent reviewer, the test author (no browser, never sees the application), the hardener and the triager. The reviewer runs on Sonnet and the others on Opus, so the review is independent in model as well as context. Each agent file's model: line sets this, with fallbacks.
  • The heldout command line does everything mechanical: fetching, checking, freezing, running, rendering and publishing. It is deterministic TypeScript, so the same inputs give the same checks.
Architecture

The system at a glance

Everything runs inside your project and a GitHub Copilot or Claude Code agent session. The application is only ever touched from the outside, the way a user or an API client would.

In plain English

Nothing about your application is baked into the skill. Where the app lives, how users sign in and which secrets it needs all sit in your project's heldout.config.json and .env. The same skill evaluates a shop, a banking demo or an internal admin tool.

The flow

One story, end to end

Eight phases, always in order, with the contract as step 1b. The right-hand column shows what each one produced for a real story: TOOL-4, "Favourites for signed-in customers", on Practice Software Testing (Toolshop).

1

Fetch script

Pulls the story's title, description and acceptance criteria, the screenshots they show and the Confluence pages they link, and binds the story to an application profile. Comments and other attachments are not read. A later fetch notices when the requirement changed.

heldout fetch KEY
TOOL-4story + criteria in a Jira custom field + 1 linked page with the API definition
1b

Contract subagents

One subagent turns the story into a structured, cited requirement contract. A second one, on a different model (Sonnet), reviews it in a fresh context. Scripts check that every item is grounded.

heldout contract KEY --pack · heldout contract KEY
TOOL-46 acceptance criteria · 6 gaps (5 how-to, found in the app) · reviewed
2

Write the tests subagent

The test author, with no browser, writes Playwright TypeScript tests for the UI and the API straight from the reviewed contract. First one test per criterion, then round the test types (functional, negative, boundary, security, idempotency, concurrency…) for what each criterion implies. Each test is one journey, tagged with its criteria, the one test type it truly proves, and the source it comes from. Its steps call the app's actions, adding the missing ones, one file each. Guessed locators are marked for hardening.

heldout scaffold KEY · heldout actions KEY · heldout lint KEY
TOOL-41 spec file, 11 tests (functional, security, idempotency, integration)

Freeze + harden subagent

A script seals every expected value before the tests meet the real application. Then the hardener makes locators, waits and API plumbing work against the live app, in the tests and the actions they call, without touching what is expected.

Run script

Preflight checks, then the full suite. Each run gets its own numbered folder that is never deleted.

TOOL-411 passed in 17.1 s, UI and API on separate hosts
5

Triage subagent

The triager classifies each failure as a script defect or an application defect, and reproduces every application defect live.

6

Verdict script

Renders the recommendation with traceability, reproduction steps and evidence.

Publish script

Attaches the verdict to the story, posts a summary comment and sets a label. Nothing else.

Setting up

Onboarding

Four commands take an empty folder to a project that is ready to evaluate stories. They work in bash, zsh and PowerShell, from the skill's GitLab repository, with any git version (init --cone keeps the top-level files on older ones).

The main agent runs the heldout commands between phases and hands each phase that needs a model to its own subagent: contract extractor, contract reviewer, test author, hardener and triager. In Copilot, choose Claude Opus in the model picker and use agent mode; in Claude Code, choose Opus with /model. Opus asks its questions in the chat, and passes --quiet to heldout run for the short digest (or set HELDOUT_QUIET=1).

Setting up

Test users

Most stories need a signed-in user. How tests get one is written once per application, as the profile's accounts recipe, and every story on that app reuses it.

Anatomy of a recipe

This is the real recipe the TOOL-4 evaluation saved for Toolshop, whose API lives on its own host. Toolshop has no call to delete an account, so the recipe has no delete and the accounts are kept, named hldout-…. The password is a reference to .env, never a value, because this file is committed.

heldout.config.json → auts.practicesoftwaretesting.accounts
{
  "password": "${env:TS_USER_PASSWORD}",
  "username": "hldout-${uid}@example.com",
  "create": { "method": "POST", "path": "/users/register",
              "body": { "first_name": "Hldout", "last_name": "Test", "email": "${username}", "password": "${password}" },
              "id": "id" },
  "token":  { "method": "POST", "path": "/users/login",
              "body": { "email": "${username}", "password": "${password}" }, "token": "access_token" },
  "authHeader": "Authorization: Bearer ${token}",
  "signIn": { "path": "auth/login", "done": "url:/account", "steps": [
    { "fill": "getByTestId('email')", "value": "${username}" },
    { "fill": "getByTestId('password')", "value": "${password}" },
    { "click": "getByTestId('login-submit')" } ] }
}

before · create · token · lookup

How a user is made and signed in over the API. before fetches what those calls need first, such as a CSRF token. lookup is a "who am I" call for apps whose sign-in answer carries no id.

delete

Optional. Without it, created accounts are kept and tagged. doctor then never creates a throw-away check account.

existing[]

Accounts someone else made. The user name may be literal or a reference. The password is always ${env:…} or ${vault:…}.

signIn · signUp

The UI sign-in as recorded steps, and how to know it worked. signIn(page, me) replays it as a precondition. signUp is the same for an app's sign-up page.

Sharing existing accounts between parallel workers

Two tests must never use the same account at the same time. Existing accounts are split between Playwright workers, and heldout run never starts more workers than the pool allows.

Worker 1
hldout.user1
hldout.user2
Worker 2
hldout.user3
hldout.user4
Worker 3
hldout.user5
hldout.user6

Workers = floor(accounts ÷ accounts-per-test). A test that needs two users at once, such as "each customer sees only their own favourites", is recorded with accounts --per-test 2.

Existing accounts outlive every run, so what a test adds to one would reach the next test. Save the call that restores an account once, e.g. accounts --reset 'DELETE /BookStore/v1/Books?UserId=${id}': it runs when a test takes the account (a crashed earlier run leaves nothing behind) and again after it, and the run reports how often accounts were taken and reset.

Everything the tests make is named with the app's data prefix, hldout unless the app's rules need another: users hldout-…@example.com, records hldout …, seed tags. Leftovers and users an app won't let tests delete are easy to find and sweep. Another prefix, once per app: init --profile <id> --data-prefix <prefix>.

In plain English

Some apps let you create test users freely. Some let you create them but not delete them. Some don't let you create them at all, and you use accounts your team already has. The evaluator handles all three. You describe your situation once, and every test simply asks for "a signed-in user".

Secrets and HashiCorp Vault

A secret is always referenced, never written. The same reference works on a laptop, in CI and against Vault.

Put a password in .env without seeing it

heldout secret APP_PASSWORD_1 --ask reads it at a hidden prompt. --generate makes a strong one for accounts the tests create.

Refuses literal passwords

accounts --add-existing --password … is rejected. It points you to --password-env or --password-vault instead.

In plain English

Your config says where a password lives, never what it is. On your laptop it comes from a private file. In CI it comes from the pipeline's protected variables. In a bigger company it comes from Vault. The evaluator also checks that no password leaked into anything you might commit.

Evaluating a story

The requirement contract

The requirement is the story's title, description and acceptance criteria, the screenshots they show and the Confluence pages they link; comments and other attachments are not part of it, and there is no API document unless one of those holds it. It comes in every shape: an acceptance-criteria field, bullets, Given/When/Then, a table, a screenshot, an OpenAPI excerpt on a linked page. A model reads it. Scripts prove that what it wrote is really in the sources.

One acceptance criterion from the TOOL-4 contract, exactly as the extractor wrote it:

Where the story leaves an expected value out, a page it links may hold it. TOOL-4's description links the team's Favourites API page; fetch saves it as Markdown beside the story, with its OpenAPI excerpt kept verbatim, and the status for a duplicate favourite is cited from there. In plain English

Before writing any test, the evaluator writes down exactly what the story promises, with a line reference for every claim, like footnotes in an essay. A second, independent reader checks the footnotes. If the story doesn't say what the right answer is, the evaluator asks you. It never peeks at what the app does and calls that the answer.

Evaluating a story

Writing the tests

The test author, who has no browser and never sees the application, writes Playwright TypeScript tests straight from the reviewed contract. heldout scaffold gives it a head start: one stub per criterion, the contract's gaps as comment lines and an empty block for the expected values. heldout actions KEY lists the app's actions its steps can call.

Each test is one user journey: an SCN-nnn id, the criteria it proves (@AC-n), exactly one @type:, a @layer:, and a // from … comment above it naming the story section, linked page or screenshot it comes from. Its steps read as journey.step('Given …'), 'When …', 'Then …'. Ambiguity is never resolved silently: it becomes // ASSUMPTION:, // OPEN-QUESTION: or @needs-clarification, and all three show up in the verdict. // OBSERVATION: notes something the story's goal implies but no criterion states, and // SEED-ENDPOINT: names a plumbing call the requirement doesn't declare.

Test types

The tests come in two passes. First, one test per criterion, the criterion as it is stated, so every criterion is covered once. Then the test author goes round the criteria again, through the types below in their order, and adds a test for each type the criterion's wording states or clearly implies that none of its tests has yet, until a round adds nothing. A type the story doesn't state or clearly imply becomes a question in the contract, not a guessed test.

Each test has exactly one type: what it truly proves. The test author reads it off the test's requirement assertions (if this fails, what has the application got wrong?), not off the steps it takes on the way: signing in first or checking a UI result through the API doesn't make a test security or integration. A test that seems to fit two types takes the more specific one, higher in the table: a refused value just outside a limit is boundary, a request without a token that is refused is security. A test that truly proves two things becomes two tests, so one failure points at one cause. The lint backs this up: it warns when a test's code doesn't match its type, such as a concurrency test that sends nothing at the same time or a composition that chains no other criterion. The type drives triage and the verdict's coverage by type, so each test is counted once. An audit requirement is tested like any other: a change the application shows (a history page) is checked by a functional test, and a record kept only in a database or log can't be seen from outside, so the verdict lists it as not verified.

A requirement that is real but can't be observed from the outside, such as a trail kept only in server logs, is listed in the verdict as not verified instead of being tested.

An excerpt of the TOOL-4 spec for Toolshop: one API test and one UI test, their steps on the app's actions (each imported straight from its own file), every expected value in the spec.

output/practicesoftwaretesting/TOOL-4/tests/tool-4.spec.ts
import { test, expect, signIn, type Account } from '../../../../heldout-support/fixtures';
import { products } from '../../../../actions/practicesoftwaretesting/api/catalogue/products';   // actions: HOW, never WHAT
import { openProduct } from '../../../../actions/practicesoftwaretesting/ui/product/open-product';
import { openFavourites } from '../../../../actions/practicesoftwaretesting/ui/account/open-favourites';

// ASSUMPTION: G2 — status of a refused duplicate: 409 (the linked Favourites API page shows it)

// @req-constants-start — expected outcomes copied verbatim from TOOL-4 (never edit during hardening)
const REQ = {
  STATUS: { CREATED: 201, NO_CONTENT: 204, UNAUTHORIZED: 401, CONFLICT: 409 },
  ADDED_MESSAGE: 'Product added to your favorites list.',
} as const;
// @req-constants-end

// from story AC-1, linked/confluence-880001-favourites-api.md §POST /favorites
test('SCN-001: A customer adds a product to favourites', { tag: ['@AC-1', '@type:functional', '@layer:api', '@P1'] }, async ({ api, journey, seed }) => {
  let me!: Account; let p!: Product; let res!: ApiResponse<Favourite>;
  await journey.step('Given I am a signed-in customer and know an existing product', async () => { me = await seed.account(); [p] = await products(api, seed, 1); });
  await journey.step('When I POST /favorites with that product_id', async () => {
    res = await api.post(EP.favorites, { headers: me.headers, data: { product_id: p.id } });
    if (res.status === REQ.STATUS.CREATED) seed.track('favourite added by the test', res.body, (f) => api.delete(EP.favorite(f.id), { headers: me.headers }));
  });
  await journey.step('Then the answer is 201 with the favourite\'s id and the product id', async () => {
    expect.soft(res.status, '[REQ AC-1] POST /favorites → 201').toBe(REQ.STATUS.CREATED);
    expect.soft(res.body?.product_id, '[REQ AC-1] POST /favorites answers the product id').toBe(p.id);
  });
});

// from story AC-5
test('SCN-005: Adding to favourites in the web shop', { tag: ['@AC-5', '@type:integration', '@layer:ui', '@P1'] }, async ({ page, api, journey, seed }) => {
  let me!: Account; let p!: Product;
  await journey.step('Given I am a signed-in customer on a product page', async () => {
    me = await seed.account(); [p] = await products(api, seed, 1);
    await signIn(page, me); await openProduct(page, p.id);
  });
  await journey.step('When I click "Add to favourites"', () => page.getByTestId('add-to-favorites').click());
  await journey.step('Then I see "Product added to your favorites list."', async () => {
    await expect(page.getByText(REQ.ADDED_MESSAGE), '[REQ AC-5] the confirmation is shown').toBeVisible();
  });
  await journey.step('And the product appears on the "Favorites" page of my account', async () => {
    await openFavourites(page);
    await expect(page.getByText(p.name), '[REQ AC-5] the product is on the Favorites page').toBeVisible();
  });
});

[REQ AC-n]

An assertion message that ties a check to its criterion. Only these can make a test fail as a requirement failure, and they stay in the spec, never in an action.

journey.step

Each Given / When / Then line is a step, so failures, screenshots and the verdict speak the requirement's language.

actions/…

Opening a page, signing in, finding a product: shared HOW code, one action per file in its domain's folder, reused by every story on the app. See Actions.

heldout lint checks traceability: every criterion has a test and a [REQ] assertion, every test has exactly one type and its criteria tags, every declared endpoint is used, no action holds a [REQ] assertion, an expectResponse or an expected literal, and no test is focused, skipped or waiting on a fixed sleep. It warns about a test without a // from source. It also type-checks the story's specs, so a draft that doesn't compile can't be frozen.

Evaluating a story

The integrity freeze

The most important guardrail: hardening may change how a test works, never what it expects.

There are only two audited exceptions, and both are listed in the verdict. integrity --amend fixes a buggy assertion implementation, such as an over-strict regular expression. integrity --snapshot --reason re-freezes after the requirement itself was revised.

Actions are not frozen, because they hold no expected values. The freeze records the hashes of the action files the draft uses (draft/actions.json), the verdict lists the ones that changed after it, and a [REQ …] assertion inside an action is a violation: it would escape the freeze.

In plain English

The answer key is sealed in an envelope before the practice round. During practice you may fix your pen or find the right room, but you may not change the answers. If someone does, the result is thrown out as inconclusive.

Evaluating a story

Hardening

A draft is written blind, so its locators and API plumbing are educated guesses. Hardening makes them real, using the first browser tier the session actually has.

1IDE browser

Browser tools of the host IDE

An integrated browser, or a browser extension the agent drives. Navigate, read the page and act step by step.

↓ not available? fall through
2Playwright MCP

The Playwright MCP server, set up by init

Accessibility snapshots and actions, each returning the Playwright code it ran. Where the tools aren't loaded, such as in CI, heldout mcp-probe drives the same server.

↓ always there
3Bundled

inspect, api-probe --chain, run --capture

An ARIA snapshot with ranked unique locators and probes. API calls or whole call chains with status, timing, shape and a redacted body. A snapshot after every step of a run.

Cookie banners and welcome dialogs that the app itself shows go in the profile's overlays: the button that closes each. Tests, the UI sign-in and the inspector click it whenever it appears, so no test has to deal with it.

Every final locator is verified by a probe: exactly one match, in the right state. Each open mechanics gap from the contract is recorded once it's found, with its evidence, for example contract TOOL-4 --resolve G4 --value … --evidence hardening/signin-steps.json (how a web shop test signs in). Stability is proven with run --label harden --repeat-each 3.

The hardener makes the actions the tests call work too, the same way: an action is mechanics to verify, never evidence. A fix keeps every other story that calls it working; an action that no longer works and is replaced is marked with actions KEY --stale "ui:product.openProduct" --evidence ….

The first story that needs users also produces the accounts recipe: the probe chain that signed up and signed in becomes accounts --from-chain, and the login steps from inspect become the UI sign-in.

Evaluating a story

Actions

Every story on the same application needs the same mechanics: where the sign-in page is, what shows that a page has loaded, which locator reaches a button, how to create and delete a record. Actions keep them as code, per application, one action per file in the folder of the domain it works on, so the tests of a later story call what earlier stories proved instead of discovering it again.

PartWhereHolds
UI actionsactions/<profile>/ui/<domain>/<action>.tsone action per file, in the folder of the area of the app it works on (auth, product, cart…): open a page and wait until it is ready, fill a form, sign in
API actionsactions/<profile>/api/<domain>/<action>.tscreate and delete a record, find one, the fields an endpoint takes, seeding and cleanup
Shared helpersactions/<profile>/<kind>/<domain>/_shared.tsoptional: helpers and types the actions of one domain share; not actions themselves
UI mapactions/<profile>/map/ui/*.jsonwhich action opens which route, waits on which anchor, uses which locators; the stories whose passing tests proved it
API mapactions/<profile>/map/api/*.jsonwhich action calls which endpoints; the stories that proved it

A domain is an area of the application as its users see it, named by what it is about (cart, favorites, account), not by the story that first needed it. Each file holds one exported function, named in kebab case after it (addFavourite → api/favorites/add-favourite.ts), with a doc comment that says what it does. It takes what it needs as parameters, imports only heldout-support/fixtures, other actions and its domain's _shared.ts, and may check its own preconditions with a plain expect(…, '… (precondition)'). It never holds what a story expects: no [REQ …] assertion, no expectResponse, no message or value the requirement says the app shows. It returns what its step produced, and the test asserts it. There is no index file: specs import each action file directly.

actions/practicesoftwaretesting/api/favorites/add-favourite.ts
import { expect, type Account, type Api, type Seed } from '../../../../heldout-support/fixtures';

Evaluating a story

Actions over a project's life

Nobody writes actions up front, and no command generates them from the application. They arrive story by story: the test author writes the ones a story needs while drafting its tests, the hardener makes them work against the live app, and the harvest records the ones the story's passing tests proved. This section follows the actions/ folder from init to the tenth story, with real output from three stories evaluated one after the other in one project on Toolshop: TOOL-1 (catalogue search, sorting and filter), TOOL-2 (registration, sign-in and lockout), then TOOL-4 (favourites for signed-in customers).

Step by step

1

init script

Creates an empty actions/ folder and sets actionsDir in heldout.config.json. It never writes an action and never overwrites the folder: a project that already has actions keeps them, and so does a second application profile added later with add-aut (its actions go in actions/<its profile>/).

heldout init --base-url https://your-app
Toolshopactions/ is empty
2

doctor script

Sees that the profile has no actions yet and says where the first ones will go. From the first story on, it lints every action file, reports possible duplicates and files off the one-action-per-file layout, counts what the maps hold, and suggests compacting them past 200 map files.

heldout doctor
Before TOOL-1✔ no actions yet — the first story's tests start them in actions/practicesoftwaretesting/ui|api/<domain>/<action>.ts
3

First story: writing the tests subagent

heldout actions TOOL-1 has nothing to list, so the test author writes each step the story needs as a new action: one file per action, named after it, in the folder of the area of the app it works on, with a doc comment that says what it does. It writes them from the contract alone, without a browser, and marks every guessed route, locator or field with // TODO(harden). That is safe before the freeze because an action never holds an expected value.

heldout actions TOOL-1 · heldout lint TOOL-1 --allow-unhardened
TOOL-17 actions in 9 files: ui/catalogue/ (open, search, sort, filter, read the cards, and _shared.ts), api/products/read-whole-catalogue.ts (and _shared.ts), api/categories/find-category-id.ts
4

Freeze script

The freeze seals the spec and the contract's oracle and records a hash of every action file the spec imports, in the story's own folder (draft/actions.json). Actions are not frozen: the hashes only let the verdict say which ones hardening changed.

heldout integrity TOOL-1 --snapshot
TOOL-1✔ Draft frozen (1 spec file(s) + requirement-contract oracle + the hashes of 9 action file(s))
5

Hardening subagent

The hardener makes each action work against the live app, as it does the tests: a verified locator, wait or field replaces each TODO(harden). It fixes HOW an action works for every caller and never bends it to one story; for a different need it adds an action. What it discovers that later stories will need becomes a new action too. An action it replaces is marked stale, with evidence.

heldout run TOOL-1 --label harden · actions TOOL-1 --stale "<key>" --evidence …
TOOL-1the shop fetches product lists with the HTTP method QUERY, not GET, so the shared wait now matches any method; a product's category is category.id, not the guessed category_id
6

Run and verdict script

Before every run, preflight lints the actions the tests import: an expected value or a [REQ …] assertion in one is an error, and a TODO(harden) left in one blocks the official run. The verdict then says how the actions took part.

7

Harvest script

After the verdict, --harvest previews and --harvest --apply writes, as new files, one per kind, the actions a passing test called: what each opens, calls and uses now, its doc comment and parameters, and the run and tests that proved it. Actions only failing tests called are left out, since they may work around a defect. Commit the action files, the new map files and the story's output together.

heldout actions TOOL-1 --harvest → --harvest --apply

update script

Replaces the skill and its scripts, and never touches actions/, the maps or output/. A newer version may check actions more strictly, so run doctor afterwards: it lints every action against the new rules and tells you what to change.

Merge conflicts: avoided by design

Shared test code usually conflicts because everyone edits the same few files: a page-object class per page, an index that re-exports every helper, one registry of what exists. Here, people (or teams) evaluate their own stories against the same application on their own branches, and each adds the actions their stories need. The folder is laid out so that adding is always creating new files, never editing shared ones:

What people do on their branchesWhat happens when the branches merge
Add new actionsEach is a new file: git merges them on its own, nothing to resolve
Harvest their storiesEach harvest is new map files, never an edit: git merges them on its own
Use, and so re-prove, an existing actionOnly new map files again; the action file is untouched
Freeze, harden, run and stage stale marksAll in the story's own folder, output/<profile>/<KEY>/ (draft/actions.json, hardening/actions-staged.json, actions-harvest.json): no other story writes there
Fix the same action, both of themA real conflict, in that one small file: the two fixes have to be reconciled anyway
Add the same action under the same nameBoth create the same file: git shows one conflict to resolve, instead of two copies
Add the same action twice, under two namesNo conflict, but a duplicate: actions --check and doctor report actions that make the same calls, or open the same routes with the same locators

What makes it work

  • One action per file, named after it, in its domain's folder, and no index. A new action is a new path, so two branches that add actions never touch the same file. Specs import each action file directly, so there is no index or barrel file that every new action would have to edit. The lint warns about a file with several actions, a file not named after its action, a file outside a domain folder and an index file, before they reach anyone else.
  • Maps that are only ever added to. Each harvest writes new files, one per kind, named by time, story and a random part (map/ui/<time>-<story>-<random>.json), so two harvests never pick the same name, even of the same story at the same second.
  • A map worked out when it is read. Every file of a kind is folded into one view: for each action and each version of what it does, the latest time it was proven, the latest time it was found stale, and the union of the stories that proved it. Taking the latest and the union gives the same result in any order, and folding a file twice changes nothing, so it doesn't matter which branch merged first. An action is stale when its latest stale mark is newer than its latest proof. Its current entry is the version proven most recently; an older proven version stays as an alternative.
  • Story files stay in the story's folder. Everything one evaluation writes about actions, apart from new action files and new map files, lives under its own output/<profile>/<KEY>/.
  • A check after merging. heldout actions --aut <id> --check, after a merge or in a CI job, lints every action file and lists possible duplicates, the actions not in the map yet and the map entries whose action is gone from the code. doctor reports the same in one line.
  • Compaction from one place. Map files pile up, one or two per story. actions --aut <id> --compact folds each kind's files into one snapshot-….json and deletes the files it folded. Run it from one place, such as a scheduled CI job or the folder's owner, and commit the snapshot with the deletions. Snapshots fold like any other map file, so a branch harvested before the compaction still merges cleanly, and a second compaction somewhere else loses nothing. doctor suggests compacting past 200 files.

What can still conflict, and what to do

The same action fixed twice

Two branches changed one action file, because the application changed or one of them bent it to a story. Reconcile the two in that file, keeping what works for every caller. The map lists the stories that proved the action: re-run one of them, and the next harvest proves the merged code.

A domain's _shared.ts

The one file that several actions of a domain share. Two people adding helpers at its end can meet on the same lines. Keep a helper in your own action file until a second action needs it, and keep _shared.ts small.

The same action under two names

--check groups them. Keep one, make the specs that import the other import it, and delete the other file. --check then lists its old map entries as gone from the code; they do no harm.

The accounts recipe

Not an action, but shared the same way: one recipe per application in heldout.config.json, saved by the first story that needs test users. Two branches saving it at the same time edit the same lines; keep the one whose story passed.

A team's routine

  1. One branch per story. Evaluate it, then commit the new and fixed action files, the new map files and the story's output/ folder together, in one merge request.
  2. Pull the main branch before starting a story, so heldout actions KEY lists what other people's stories have proven since.
  3. After merging, or in a CI job on the main branch: heldout actions --aut <id> --check.
  4. Now and then, from one place only: heldout actions --aut <id> --compact, committed with its deletions. --log shows what the maps learned, when and from which story.

Seeding and teardown

Every test creates the data it needs, uniquely named, and removes it afterwards, even when the test fails. It never relies on records that happen to exist.

Resilient by design

Seed calls retry once on dropped connections and 502, 503 or 504, wait on Retry-After for 429, and ask the server for fresh answers.

One line tells you what happened

Every run ends with a summary: records created, cleaned up, already gone, kept by design, or left behind, with advice for each kind of cleanup error.

In plain English

Each test sets its own table, eats, and clears up. If setting the table fails, the test says "couldn't set up" rather than blaming the recipe it was meant to check. Afterwards you get a one-line receipt of what was created and what, if anything, was left behind.

Triage

A failing test is a question, not an answer. Was the test wrong about the mechanics, or is the app wrong about the requirement?

CategoryMeaningEffect on the verdict
APPLICATION_DEFECTThe app doesn't do what the requirement says, reproduced liveFAIL, pending the reviewer
SCRIPT_DEFECTThe test is wrong about mechanics: a locator, a wait, a path, a payload shaperepair, then re-run everything
ENVIRONMENT_ISSUEThe app is down, the network failed, a gateway answered 502 to 504re-run; INCONCLUSIVE if it persists
FLAKYFailed, then passed on retry, or failed only some repeatsPASS WITH WARNINGS
BLOCKEDA precondition couldn't be set up, so the test wasn't evaluatedINCONCLUSIVE until the seed works

Script defects are repaired, mechanics only, and the whole suite runs again. Decisions carry over only to failures with an identical signature. After three repair cycles, anything still unexplained stays NEEDS_INVESTIGATION.

Non-negotiable guardrails

  • Held-out isolation. Tests come only from the story (title, description, acceptance criteria, the screenshots they show, the Confluence pages they link) and black-box observation.
  • Hardening changes how, never what. Two audited exceptions, both shown in the verdict.
  • Actions are how, never what. They hold no [REQ] assertion, expectResponse or expected value, so the test author may call them before the freeze; lint and integrity refuse anything else. An action is shared: fix how it works for every caller, never bend it to one story. One action per file, named after it, in its domain's folder.
  • Surface ambiguity. // ASSUMPTION:, // OPEN-QUESTION: and @needs-clarification all appear in the verdict.
  • No application defect without live reproduction.
  • A person decides. No issues are created, transitioned or assigned.
  • A bounded repair loop of at most three cycles.
  • Runs are history. Never deleted, renamed or renumbered.
  • Seed, don't assume; and secrets stay references.
