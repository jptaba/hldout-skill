The held-out evaluator

An AI agent skill for GitHub Copilot or Claude Code that takes one Jira story, writes independent acceptance tests from the requirement alone, runs them against the live application, and hands a person an evidence-backed recommendation: does the app do what the story asked for?

What it is

In plain English

Imagine an exam written by someone who has read the syllabus but has never seen the student's homework. That is a held-out test. The term comes from machine learning, where you keep some data aside so a model can't simply memorise the answers.

Here, the "syllabus" is a Jira story and the "student" is your application. The evaluator reads only the story: its title, description and acceptance criteria, the screenshots they show and the Confluence pages they link. It never looks at the application's code or the developers' own tests. So when a test fails, it's a sign that the application drifted from what was asked for, not that the test copied a mistake.

It never files bugs by itself. It writes a verdict with evidence and reproduction steps, and a person confirms or rejects each finding.

Independent

Tests come from the requirement only. The expected values are sealed before the tests ever touch the application.

Evidence first

Every requirement is quoted from cited lines. Every failure is reproduced live and shipped with curl commands, screenshots and traces.

A person decides

The verdict is a recommendation with a confirm, reject or clarify box per finding. It creates no Jira issues.

Who does what
  • You ask Opus, in GitHub Copilot's agent mode or in Claude Code: "Run a held-out evaluation of ABC-123." That is your last step until the verdict: from the fetch on, Opus asks nothing and waits for nothing. What a vague criterion leaves open is listed in the verdict as a question for the story's owner.
  • Opus follows the skill: it reads the story, writes the tests, hardens them against the app, triages failures and writes the verdict.
  • Five subagents do the phases that need a model, each in a fresh context: the contract extractor and its independent reviewer, the test author (no browser, never sees the application), the hardener and the triager. The reviewer runs on Sonnet and the others on Opus, so the review is independent in model as well as context. Each agent file's model: line sets this, with fallbacks.
  • The heldout command line does everything mechanical: fetching, checking, freezing, running, rendering and publishing. It is deterministic TypeScript, so the same inputs give the same checks.
Architecture

The system at a glance

Everything runs inside your project and a GitHub Copilot or Claude Code agent session. The application is only ever touched from the outside, the way a user or an API client would.

In plain English

Nothing about your application is baked into the skill. Where the app lives, how users sign in and which secrets it needs all sit in your project's heldout.config.json and .env. The same skill evaluates a shop, a banking demo or an internal admin tool.

Gaps: what the story doesn't say

The extractor records every missing element as a gap and says what kind it is. The kind decides where an answer may come from, and that rule keeps the tests independent of the application.

Checks across setups: variants

When a story says its criteria must hold for every user type, data set or other setup, the contract records each dimension as a variant: the values the story names and the criteria it applies to. The reviewer checks them like any other item. From there the scripts hold the grid together:

  • Every combination needs a test. A criterion with two variants needs every pair (3 user types × 3 categories is 9 tests). Each test carries a @variant:<key>=<value> tag per variant, and the lint refuses a combination no test covers, by name: AC-1 must be tested in 3 setup(s) and 1 have no test: user-type=administrator.
  • Kinds of user are accounts with roles. Existing accounts get a role once (accounts --add-existing … --role admin), and a test asks for the kind it needs: seed.account('administrator', { role: 'admin' }). A guest takes no account. See Test users.
  • The verdict shows the grid as it ran, from the tags of the tests that actually executed. A required setup that didn't run is a warning, never a silent pass.

What the scripts check

The models understand language; the scripts don't need to. They only check that what a model wrote is grounded and traceable, and refuse to go on when it isn't.

anchoring

Each acceptance criterion is a verbatim quote, found at the line it cites.

coverage

Every requirement-bearing source line is captured or dismissed with a reason, so nothing is silently dropped.

literal grounding

Every status, number, quoted message and path in an expected outcome exists in a source or in an answered gap.

review hash

A review counts only for the exact contract it reviewed; any edit needs a new review.

traceability lint

Every criterion has a test and a [REQ AC-n] assertion; every test has one @type and a // from source.

freeze

After hardening, every frozen assertion and constant is unchanged, or changed only through an audited amendment. Journeys may carry no expected value, which is why the author may use them before the freeze.

Setting up

Onboarding

Clone the skill once, then run its setup script in the folder of the project that will hold the tests. Two commands take an empty folder to a project that is ready to evaluate stories, and the second one, without the address, is also how the project is updated later.

PowerShell
git clone --depth 1 <skill-repository-url> "$HOME/heldout-skill"
& "$HOME/heldout-skill/setup.ps1" -BaseUrl https://your-app
bash, zsh, Git Bash
git clone --depth 1 <skill-repository-url> "$HOME/heldout-skill"
"$HOME/heldout-skill/setup.sh" --base-url https://your-app

Setup pulls the clone, checks Node (20.11 or newer), runs the skill's init --install and then doctor. Pass -Project <folder> (--project) to set up another folder than the current one, -Ci gitlab (--ci gitlab) for a regression pipeline, and anything init takes after it, such as --api-base-url or --name. If PowerShell refuses to run scripts: powershell -ExecutionPolicy Bypass -File "$HOME/heldout-skill/setup.ps1" -BaseUrl https://your-app.

Updating, on any machine

Run the same setup without the address, in the project's folder: it pulls the skill and updates the project. That works for a project that has already been pushed to its own repository and cloned somewhere else: anyone with a clone of the skill runs setup in their clone of the project. The project records which skill it has in .github/skills/heldout-evaluator/SOURCE.json, the skill's remote and commit, never a path on someone's machine, and doctor shows it. Files the project changed since they were copied are kept as they are, and doctor lists them.

How a user is made and signed in over the API. before fetches what those calls need first, such as a CSRF token. lookup is a "who am I" call for apps whose sign-in answer carries no id.

delete

Optional. Without it, created accounts are kept and tagged. doctor then never creates a throw-away check account.

existing[]

Accounts someone else made. The user name may be literal or a reference. The password is always ${env:…} or ${vault:…}.

signIn · signUp

The UI sign-in as recorded steps, and how to know it worked. signIn(page, me) replays it as a precondition. signUp is the same for an app's sign-up page.

Sharing existing accounts between parallel workers

Two tests must never use the same account at the same time. Existing accounts are split between Playwright workers, and heldout run never starts more workers than the pool allows.

Workers = floor(accounts ÷ accounts-per-test). A test that needs two users at once, such as "each customer sees only their own favourites", is recorded with accounts --per-test 2.

Kinds of users. When stories need an administrator, a customer and a second customer, each existing account gets its role once (accounts --add-existing … --role admin), and a test asks for the kind a step needs: seed.account('administrator', { role: 'admin' }), seed.account('another customer', { role: 'customer' }). Each worker gets its own share of every role, so runs start no more workers than the scarcest role has accounts. Roles work next to accounts the tests create: without a role, seed.account() still creates one.

Existing accounts outlive every run, so what a test adds to one would reach the next test. Save the call that restores an account once, e.g. accounts --reset 'DELETE /BookStore/v1/Books?UserId=${id}': it runs when a test takes the account (a crashed earlier run leaves nothing behind) and again after it, and the run reports how often accounts were taken and reset.

Everything the tests make is named with the app's data prefix, hldout unless the app's rules need another: users hldout-…@example.com, records hldout …, seed tags. Leftovers and users an app won't let tests delete are easy to find and sweep. Another prefix, once per app: init --profile <id> --data-prefix <prefix>.

In plain English

Some apps let you create test users freely. Some let you create them but not delete them. Some don't let you create them at all, and you use accounts your team already has. The evaluator handles all three. You describe your situation once, and every test simply asks for "a signed-in user".

Evaluating a story

The requirement contract

The requirement is the story's title, description and acceptance criteria, the screenshots they show and the Confluence pages they link; comments and other attachments are not part of it, and there is no API document unless one of those holds it. It comes in every shape: an acceptance-criteria field, bullets, Given/When/Then, a table, a screenshot, an OpenAPI excerpt on a linked page. A model reads it. In plain English

Before writing any test, the evaluator writes down exactly what the story promises, with a line reference for every claim, like footnotes in an essay. A second, independent reader checks the footnotes. If the story doesn't say what the right answer is, the evaluator doesn't stop to ask: it tests what it can and puts the question to the story's owner in the verdict. It never peeks at what the app does and calls that the answer.

Evaluating a story

Writing the tests

The test author, who has no browser and never sees the application, writes Playwright TypeScript tests straight from the reviewed contract. heldout scaffold gives it a head start: one stub per criterion, the contract's gaps as comment lines and an empty block for the expected values. heldout journeys KEY lists the app's journeys its steps can call.

Each test is one user journey: an SCN-nnn id, the criteria it proves (@AC-n), exactly one @type:, a @layer:, and a // from … comment above it naming the story section, linked page or screenshot it comes from. Its steps read as journey.step('Given …'), 'When …', 'Then …'. Ambiguity is never resolved silently: it becomes // ASSUMPTION:, // OPEN-QUESTION: or @needs-clarification, and all three show up in the verdict. // OBSERVATION: notes something the story's goal implies but no criterion states, and // SEED-ENDPOINT: names a plumbing call the requirement doesn't declare.

Test types

The tests come in two passes. First, one test per criterion, the criterion as it is stated, so every criterion is covered once. Then the test author goes round the criteria again, through the types below in their order, and adds a test for each type the criterion's wording states or clearly implies that none of its tests has yet, until a round adds nothing. A type the story doesn't state or clearly imply becomes a question in the contract, not a guessed test.

Each test has exactly one type: what it truly proves. The test author reads it off the test's requirement assertions (if this fails, what has the application got wrong?), not off the steps it takes on the way: signing in first or checking a UI result through the API doesn't make a test security or integration. A test that seems to fit two types takes the more specific one, higher in the table: a refused value just outside a limit is boundary, a request without a token that is refused is security. A test that truly proves two things becomes two tests, so one failure points at one cause. The lint backs this up: it warns when a test's code doesn't match its type, such as a concurrency test that sends nothing at the same time or a composition that chains no other criterion. The type drives triage and the verdict's coverage by type, so each test is counted once. An audit requirement is tested like any other: a change the application shows (a history page) is checked by a functional test, and a record kept only in a database or log can't be seen from outside, so the verdict lists it as not verified.

Evaluating a story

The integrity freeze

The most important guardrail: hardening may change how a test works, never what it expects.

There are only two audited exceptions, and both are listed in the verdict. integrity --amend fixes a buggy assertion implementation, such as an over-strict regular expression. integrity --snapshot --reason re-freezes after the requirement itself was revised.

Journeys are not frozen, because they hold no expected values. The freeze records a hash of each journey in the files the draft uses (draft/journeys.json; comments don't count), the verdict lists the journeys that changed after it, and a [REQ …] assertion inside a journey file is a violation: it would escape the freeze.

Journeys

Every story on the same application needs the same mechanics: where the sign-in page is, what shows that a page has loaded, which locator reaches a button, how to create and delete a record. Journeys keep them as code, one file per area of the application, and a registry next to them says what each one touches, what must run before it and which stories proved it. A domain is an area of the application as its users see it, named by what it is about (cart, favorites, account), not by the story that first needed it. Every exported function of a domain's file is a journey, with a doc comment that says what it does; helpers its journeys share stay in the file, not exported. A journey takes what it needs as parameters, imports only heldout-support/fixtures and other domains' journeys, and may check its own preconditions with a plain expect(…, '… (precondition)'). It never holds what a story expects: no [REQ …] assertion, no expectResponse, no message or value the requirement says the app shows. It returns what its step produced, and the test asserts it.

Journeys over a project's life

Nobody writes journeys up front, and no command generates them from the application. They arrive story by story: the test author writes the ones a story needs while drafting its tests, the hardener makes them work against the live app, and the harvest records in the registry the ones the story's passing tests proved. Many people, one application: merging

People (or teams) evaluate their own stories against the same application on their own branches, and each adds the journeys their stories need. The journey files are grouped by domain, so most branches touch different files or different places in one; the registry is one file every harvest writes, so two harvests often meet there. A conflict in the registry never needs reading line by line: one command settles it.

What journeys --resolve does

  • Reads both sides of the conflict markers git left in registry.yml (a diff3 base section is ignored).
  • Keeps every journey either side has, and for one both have: the later proof with every story that proved it, the later stale mark, and the prerequisites both sides agree on.
  • Brings it in line with the code that is now merged: journeys that were moved or renamed get their new place, journeys that are gone are dropped.
  • Leaves it ready to commit: git add journeys/registry.yml. A wrong guess costs little: the next passing story that uses a journey proves it again.

What else can conflict, and what to do

The same journey fixed twice

Two branches changed one journey, because the application changed or one of them bent it to a story. Reconcile the two in its domain's file, keeping what works for every caller. The registry lists the stories that proved the journey: re-run one of them, and the next harvest proves the merged code.

Two journeys added at the end of one file

Git sees both branches adding lines at the same place. Keep both functions. Adding a journey next to the ones it belongs with, rather than at the very end, makes this rarer.

The same journey under two names

--check groups them. Keep one, make the specs that import the other import it, and delete the other function. The next --sync or harvest drops its registry entry.

The accounts recipe

Not a journey, but shared the same way: one recipe per application in heldout.config.json, saved by the first story that needs test users. Two branches saving it at the same time edit the same lines; keep the one whose story passed.

A team's routine

  1. One branch per story. Evaluate it, then commit the new and fixed journey files, registry.yml and the story's output/ folder together, in one merge request.
  2. Pull the main branch before starting a story, so heldout journeys KEY lists what other people's stories have proven since.
  3. A merge conflict in registry.yml: heldout journeys --resolve, then git add it.
  4. After merging, or in a CI job on the main branch: heldout journeys --check.

Seeding and teardown

Every test creates the data it needs, uniquely named, and removes it afterwards, even when the test fails. It never relies on records that happen to exist.

Resilient by design

Seed calls retry once on dropped connections and 502, 503 or 504, wait on Retry-After for 429, and ask the server for fresh answers.

One line tells you what happened

Every run ends with a summary: records created, cleaned up, already gone, kept by design, or left behind, with advice for each kind of cleanup error.

In plain English

Each test sets its own table, eats, and clears up. If setting the table fails, the test says "couldn't set up" rather than blaming the recipe it was meant to check. Afterwards you get a one-line receipt of what was created and what, if anything, was left behind.

Triage

A failing test is a question, not an answer. Was the test wrong about the mechanics, or is the app wrong about the requirement?

CategoryMeaningEffect on the verdict
APPLICATION_DEFECTThe app doesn't do what the requirement says, reproduced liveFAIL, pending the reviewer

Script defects are repaired, mechanics only, and the whole suite runs again. Decisions carry over only to failures with an identical signature. After three repair cycles, anything still unexplained stays NEEDS_INVESTIGATION.

Non-negotiable guardrails

  • Held-out isolation. Tests come only from the story (title, description, acceptance criteria, the screenshots they show, the Confluence pages they link) and black-box observation.
  • Hardening changes how, never what. Two audited exceptions, both shown in the verdict.
  • Journeys are how, never what. They hold no [REQ] assertion, expectResponse or expected value, so the test author may call them before the freeze; lint and integrity refuse anything else. A journey is shared: fix how it works for every caller, never bend it to one story. One file per domain; the registry is written by the tools, never by hand.
  • Surface ambiguity. // ASSUMPTION:, // OPEN-QUESTION: and @needs-clarification all appear in the verdict.
  • No application defect without live reproduction.
  • A person decides. No issues are created, transitioned or assigned.
  • A bounded repair loop of at most three cycles.
  • Runs are history. Never deleted, renamed or renumbered.
  • Seed, don't assume; and secrets stay references.
