The guide

The held-out evaluator

A verdict you can trust and check on whether a running application does what a Jira story asks, judged only from what the story says, by really testing the live application. It works in GitHub Copilot and in Claude Code, on any web application or API.

Start here

What it is

Someone must accept or reject a story. The evaluator gives them a verdict with the evidence for it, without them doing the testing: PASS PASS WITH WARNINGS FAIL or INCONCLUSIVE, each finding with steps a person can repeat in minutes, the questions the story leaves open, and what was not tested.

Held-out

What a test expects comes from the story alone, never from the application's code, its developers' tests or what the application happens to do. Agents may look at the live application as much as they need, to understand the story and to operate the application; where the two differ, the story wins and the difference is shown to the story's owner. That is what lets the evaluator catch an implementation that drifted from what was asked.

The tests are a deliverable too: every check is described in plain English beside the verdict, with the command that runs it again. The verdict is a recommendation; a person decides, and the evaluator files nothing in Jira.

The design at a glance

The expected values live in one reviewed file, the story's contract with its checks. Everything after it changes how a test is done, never what it expects.

Start here

Three roles

Three subagents, each in a fresh context, do the phases; a coordinating agent (or heldout drive) runs the commands between them. Each starts from its brief, which the tool prints: npm run heldout -- brief KEY.

Contract extractor

heldout-contract-extractor

Reads the story's numbered evidence and writes the contract: each criterion quoted, the rules, the gaps, and for each criterion the fewest checks that could prove it false, every expected value copied from the line it cites.

Contract reviewer

heldout-contract-reviewer

In a fresh context, confirms every item against the evidence: supported, misread, invented or missing. Its review is bound to the contract's hash, and the builder never writes it.

Operator

heldout-operator

Makes the generated tests run against the live application, the shared journeys with them, proves them stable, then reproduces each failure the tool could not replay and decides why it failed.

Using it

Setting a project up

A project is a folder of its own, outside the application's repository (the people who build the story never see its tests). From a clone of the skill:

PowerShell or bash, in the project's folder
<clone>/setup.ps1 -BaseUrl https://your-app.example      # or setup.sh --base-url …
npm run heldout -- accounts --add-existing --username qa1@example.com --password-env APP_PASSWORD_1 --role customer
npm run heldout -- secret APP_PASSWORD_1 --ask                 # typed by a person, never by an agent
npm run heldout -- map --survey                                # what a person sees before signing in
npm run heldout -- map --add "A web shop that sells and rents tools"
npm run heldout -- doctor

Setup is the only time anyone is asked anything. It ends with a few lines of what the application is (its purpose, areas, kinds of user, words): the first entries of what is known of it. Secrets stay in .env or Vault and are referenced as ${env:NAME} or ${vault:path#field}.

Using it

Asking for a verdict

GitHub Copilot

Pick the heldout-evaluator agent in the agents dropdown, with Opus, and ask: "Run a held-out evaluation of ABC-123". It runs advance and hands each phase to its subagent.

Claude Code

Ask the same in the project's folder: the main agent follows the skill and delegates to the subagents with its Agent tool. Or run the story with nobody watching (below).

When it is done you get the verdict and why, each finding with how to reproduce it, the questions for the story's owner, where the application and the story differ, and what the story cost.

Using it

Running with nobody watching

npm run heldout -- drive KEY runs the same steps as advance and starts each subagent itself, headlessly, through Claude Code's command line, with the project's own settings, browser server and approvals. What each subagent cost goes into the story's history. Run it again after a usage limit: it picks the story up from the files. The benchmark and CI use it; in GitHub Copilot the coordinator agent stays the entry point.

How it works

The checks

A check is a few lines of data a reviewer can read: the starting state and the action in words, and each expected value with its comparator and the line of the story it came from. A value the cited line does not hold is refused.

2-contract/contract.json, one check of AC-3
{ "id": "C3.1", "title": "a coupon of 15% lowers the total", "type": "functional", "layer": "ui",
  "given": ["a cart with one rental of 40.00"], "when": ["the shopper applies the coupon RENT15"],
  "expect": [{ "id": "C3.1.a", "what": "the total shown", "comparator": "equals", "value": 34, "source": "story.md#L12" }] }
  • The fewest checks that could prove a criterion false: its plain case, each boundary and each refusal the story states, at most four a criterion; variants of one check are rows of a table.
  • Comparators: equals, contains, matches, one-of, at-least, at-most, status, absent, present, and the relations ordered, distinct and same-as, so no test works a comparison out on its own.
  • Gaps: what the story does not say. About how to operate the application, it is discovered later; about what is correct, it is assumed with one reading or left open, and the verdict asks the owner.
How it works

Tests that run

The tests are generated from the checks, one a check. The operator fills in each step and where each actual value is read; what is expected is never written in a test.

4-hardening/abc-3.spec.ts, after the operator
test('SCN-005: a coupon of 15% lowers the total', { tag: ['@AC-3', '@type:functional'] }, async ({ page, seed }) => {
  await journey.step('Given a cart with one rental of 40.00', async () => { await cartWithRental(page, seed, 40); });
  await journey.step('When the shopper applies the coupon RENT15', async () => { await applyCoupon(page, 'RENT15'); });
  await journey.step('Then the total shown is 34', async () => {
    const actual = await page.getByTestId('cart-total').textContent();
    expectCheck('C3.1.a', actual);
  });
});

The steps call journeys: shared functions per area of the application (journeys/fixtures/cart.ts), the reusable how. A journey a passing test used is recorded as proven, so the next story starts from it.

How it works

What the freeze protects

heldout integrity KEY compares the tests that run with the frozen draft and the contract. It is violated, and the verdict is then INCONCLUSIVE, when:

  • an expectation the draft names is no longer asserted, or one is added;
  • a test states an expectation of its own (expect(…)) instead of naming one;
  • an actual value is not read from the application: a literal, or what the test itself sent, which would make the check pass whatever the application does;
  • a journey asserts anything a requirement expects;
  • the contract's expected values changed after the freeze. The one audited exception: a check corrected in the contract, reviewed again and re-frozen with a reason, which the verdict shows.
How it works

Triage and verification

Every failure is a script defect, an application defect, an environment issue, flaky, blocked or still to investigate. The automatic classification is only a hypothesis. A sure failure of an API answer is sent again by the tool, outside the test, twice: the same answer both times confirms it. The operator reproduces the rest live, by hand, before calling any of them a defect, and failures of one cause become one finding.

Then each finding is checked once more before anything is published: its tests run again on their own, unchanged. A finding that does not fail the same way again is reported as needing investigation, not as a defect.

How it works

The verdict and the catalogue

The first screen of verdict.md answers the reader's questions and nothing else: the verdict and why, each finding in a line, the questions for the story's owner, what was not tested, and where the application and the story differ. Each finding follows in full: the requirement, expected against actual, the shortest way to reproduce it, the evidence, whether it held when verified, and a decision box for the owner. The record the verdict rests on comes last.

catalogue.md beside it says every check in plain words: the starting state, what is done, what is expected and where the story says so, its result, and the command that runs it again. It is written from the reviewed checks, so it cannot describe a test other than the one that ran.

How it works

What is known of the application

Every use of the live application leaves what was learned, so the next agent and the next story go to the application only for what is missing. One store per application, application-map/<profile>/knowledge.jsonl, one entry a line, each one of four kinds:

KindWhat it holds
aboutwhat the application is: its purpose, areas, kinds of user, words
howhow it is operated: a route, a wait it needs, an answer's shape, the call a page makes
seenwhat it was seen to accept, refuse or compute, said as what happened
dataits accounts, how a precondition is made, what a run leaves and how it is cleaned up

An entry is written only when it is new, and corrected (--fix, --remove) in the step that finds it wrong; using it writes nothing, and it records no story, date or run. None of it is ever an oracle: a contract that names it is refused, and a decision needs this story's own probe.

The controls

RiskControl
Expecting what the application doesevery expected value cites its line of the story and is grounded in it; the reviewer judges a check that reads an unclear line the application's way as misread; a difference an agent sees is a discrepancy the verdict lists
Invented requirementscriteria quoted from cited lines, every source line accounted for, an independent review bound to the contract's hash
A check that passes vacuouslythe actual value must be read from the application; integrity refuses a literal or the test's own input
A wrong findingreplay or live reproduction, then verification before publishing
Teaching to the testthe project is separate from the application's repository; the implementers get the published verdict only
Instructions hidden in a story or a pageuntrusted content is data, flagged and listed in the verdict, never followed
Secretsreferences only, redaction while running, a scrub after each run, a check before publishing

Who decides what, and how the controls map to the NIST AI RMF and the OWASP lists, is in the skill's references/governance.md.
