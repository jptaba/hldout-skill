Application and domain knowledge

What the evaluator knows of your application, and where that knowledge stops

Each story teaches the agents something about the application: what its areas are called, how a page is operated, what a call answers, how a test makes its own data. That knowledge is kept, one store per application, so the next story starts from it instead of finding it all again. It explains the application's words and mechanics. It never says what is correct: that comes from the story alone.

Kept between stories

One file per application, application-map/<profile>/knowledge.jsonl, committed with the project. A later story goes to the application only for what is not known yet.

Read in every phase

Each subagent's brief carries the part it needs: the contract's agents what the application is; the operator all of it, or the list of domains to read from.

Written only when new, with proof

A story's entry cites the probe that showed it. Saying the same thing again writes nothing; an entry found wrong is corrected where it is found.

Never an oracle

A contract that names the store is refused, and so is a triage decision that rests on it. The story says what is correct; this story's own probe says what the application does.

Two stores: words and code

Knowledge is what a reader needs to know, in sentences. Journeys are the same mechanics as code the tests call: one file per domain, journeys/fixtures/cart.ts, every journey documented, never holding an expected value.

Where it stops

Three places refuse knowledge used as proof, with the message the agent gets.

The contract

A criterion, a rule, an error, a value or a gap's answer that names the store.

rests-on-knowledge: a value comes from the story's sources alone. That knowledge only explains a word; cite the story's line instead

A triage decision

A failure decided by what an earlier story saw, with no probe of this one.

A decision rests on this story's own reproduction: … Reproduce the failure and cite the probe (P7). Nothing was written.

Evidence

An entry cited where evidence is asked for.

K1f2348 is what an earlier story saw or was told, not evidence for this one: cite this story's probe (P7) or run.

An entry also holds no story, date, run or record id, so a story that learned nothing leaves the file byte for byte as it was, and two branches merge by keeping both sides' lines.

For leadership

What it buys, what it costs, where it stands

The outcomefour verdicts, and why held-out

A verdict a person can trust and check, without doing the testing

Someone has to accept or reject each story. The evaluator gives them one of four recommendations, with the evidence behind it, and raises nothing in Jira on its own.

PASS

The application did what every criterion states, in every test that ran.

PASS WITH WARNINGS

Nothing failed, but something was not tested, flaky, or rests on a question for the owner.

FAIL

At least one defect was reproduced against the live application, and verified once more.

INCONCLUSIVE

The evaluation could not judge: the environment failed, or a failure is still unexplained.

Why "held-out"

What each test expects comes from the story alone, and every expected value cites the line of the story it came from. The agents may look at the application as much as they need, to understand it and operate it, but where the application differs from the story, the story wins and the difference is shown to the story's owner. That is what lets the evaluator catch an implementation that drifted from what was asked, which a test written by watching the application never could.

The stories are implemented by another group of agents. This project checks their work from the outside, as an independent reviewer would.

What stays with a person

  • Acting on the verdict: each finding has a confirm, reject or clarify box for the story's owner.
  • What is correct: open questions go to the owner through the verdict; no agent answers them.
  • Publishing, when a team wants to read the verdict first.
  • Secrets, typed by a person, never by an agent.
Asking for a verdictone sentence

One sentence starts it

GitHub Copilot

Pick the heldout-evaluator agent in the agents dropdown, with Opus, and ask "Run a held-out evaluation of ABC-123".

Claude Code

Ask the same in the project's folder, or run the whole story with nobody watching: npm run heldout -- drive ABC-123.

Nobody is asked anything from the fetch to the published verdict. What the story leaves unclear is tested as far as it can be and put to the story's owner in the verdict.

Reading the resultthe verdict and the catalogue

The verdict's first screen

  • The verdict and why, in one line.
  • Findings, one line each: the criterion, the suggested severity, what is wrong.
  • Questions for the story's owner: what the story does not settle.
  • Not tested: a criterion with no test, a setup no test covered, a test that did not run.
  • Where the application and the story differ: noted by the agents, and never used as an expected value.

Each finding follows in full: the requirement, expected against actual, the steps and API calls to reproduce it, a screenshot, whether it held when verified, and a decision box.

The catalogue: every test in plain English

7-verdict/catalogue.md sits beside the verdict. For each criterion and each check: the starting state, what is done, what is expected and the line of the story that says so, the result, and one command to run it again.

# run one check again
npm run heldout -- run ABC-123 --label repro --grep "SCN-005:"
# run every check again
npm run heldout -- run ABC-123 --label repro

The architecturescripts and three agents

Scripts do what is the same every time; agents do what needs judgement

heldout-contract-extractor

Writes the oracle

The contract: criteria quoted from cited lines, gaps, and per criterion the fewest checks that could prove it false.

heldout-contract-reviewer

Reviews it

A fresh context, the evidence only; its review is bound to the contract's hash.

heldout-operator

Operates the application

Makes the generated tests run, then triages and repairs, in one context.

heldout advance KEY is a state machine read from the files on disk: it runs every script step that comes next and stops at a subagent, printing its task and its brief. heldout drive KEY runs the same machine and starts each subagent itself through Claude Code's command line.

From check to running test

// generated from the check; the operator fills in the steps and where `actual` is read
test('SCN-005: a coupon of 15% lowers the total', { tag: ['@AC-3', '@type:functional'] }, async ({ page, seed }) => {
  await journey.step('When the shopper applies RENT15', async () => { await applyCoupon(page, 'RENT15'); });
  await journey.step('Then the total shown is 34', async () => {
    const actual = await page.getByTestId('cart-total').textContent();
    expectCheck('C3.1.a', actual);   // the expected 34 lives only in the frozen contract
  });
});

Code and rulesphases, triage, the benchmark, the rules

The scripts, by phase .github/scripts/

Imports follow the phases' order and never run backwards; a command module never imports another command (both are tested).

Triage, replay and verification

CategoryMeaningEffect
APPLICATION_DEFECTThe application does not do what the requirement says, reproducedFAIL
SCRIPT_DEFECTThe test is wrong about mechanicsRepair and run again, at most three times
ENVIRONMENT_ISSUEDown, rate-limited, a sandbox someone changedINCONCLUSIVE if it persists
FLAKYFailed only some of the timePASS WITH WARNINGS
BLOCKEDA precondition could not be madeINCONCLUSIVE until it can
NEEDS_INVESTIGATIONNot settled, or not held when verifiedINCONCLUSIVE
  • Replay: a sure API failure is sent again outside the test, twice, signing in afresh; the same answer both times confirms it with no agent.
  • Live reproduction: the operator reproduces the rest with probes, each logged as Pn and cited by its decision.
  • Verify: each finding's tests run again on their own; it holds when the same check fails again, whatever record it named.

The benchmark dev/bench.ts · maintainers only

Toolshop runs locally behind a proxy that switches 14 known faults on per run. Five stories were written by an author who had not read the evaluator; each has a key naming the faults that break it. A score runs the story's tests with no fault and with each fault alone: a fault counts as found when a finding's test fails with only that fault on and passes with none.

npx tsx dev/bench.ts up                 # the app, fresh data, the fault proxy
npx tsx dev/bench.ts new p11 --stories SHOP-2
npx tsx dev/bench.ts eval p11 SHOP-2     # headless, through heldout drive
npx tsx dev/bench.ts score p11 SHOP-2
npx tsx dev/bench.ts report

Rules of the repository

Greenfield and lean

No compatibility shims; one fact in one place; instruction files carry only what a change needs.

Application-agnostic

The skill never names an application, its routes or values; demo applications live under demo/.

Commands, not scripts

No agent writes a script of its own; a need no command meets is a tool gap that becomes a command.

Green before push

npm run typecheck and npm run test:skill, then a small commit on master. A bug fix ships with a test that fails without it.
